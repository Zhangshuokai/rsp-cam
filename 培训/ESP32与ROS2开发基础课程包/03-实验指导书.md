## 实验一：环境搭建与固件烧录

**实验目的**
1. 学会识别开发板与串口（CH343 → COM 口）。
2. 安装并使用 `esptool` / `mpremote` 工具链。
3. 完成 MicroPython 固件烧录并进入 REPL。

**器材与环境**：ESP32-S3 N16R8 开发板、数据 USB 线、Windows 电脑（已装 Python 3.10+）。

**任务与步骤**

1. 安装工具（每台电脑一次）：
   ```powershell
   python -m pip install esptool mpremote
   python -m esptool version
   ```
2. 插上开发板，列出串口（也可用设备管理器找 "CH343"）：
   ```powershell
   python -m mpremote devs
   [System.IO.Ports.SerialPort]::GetPortNames()
   ```
3. 探测芯片（把 COM13 换成你的端口）：
   ```powershell
   python -m esptool --port COM13 --baud 460800 flash-id
   ```
   应看到 `ESP32-S3`、16MB Flash 等信息。
4. 观察出厂固件：用串口监视器（115200）打开对应 COM 口，应看到约每 1.5 秒一行 `example: log -> UART`，且按 Ctrl-C 无 REPL。
5. 烧录 MicroPython（**先擦除，再烧到 0x0**；中文路径必须加引号）：
   ```powershell
   python -m esptool --port COM13 --baud 460800 erase-flash
   python -m esptool --port COM13 --baud 460800 write-flash -z 0x0 "ESP32-S3开发板N16R8焊接\固件\GENERIC_S3-20220618-v1.19.1.bin"
   ```
6. 进入 REPL 验证（退出时按 Ctrl-]）：
   ```powershell
   python -m mpremote connect COM13
   ```
   在 `>>>` 后执行 `print("hello esp32")` 与 `import sys; print(sys.implementation)`。

**验收标准**
- [ ] 提交 `flash-id` 输出，能指出芯片型号与 Flash 容量。
- [ ] REPL 中成功打印 `hello esp32` 与 MicroPython 版本信息。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| `could not open port` | 端口被占用/端口号写错 | 关闭 Thonny、串口助手等；重新确认端口号 |
| `mpremote` 首次连接报 "could not enter raw repl" | 首次进入 raw REPL 偶发失败 | 等 2 秒重试一次，不是硬件问题 |
| 烧录后没有反应 | 需要复位 | `python -m mpremote connect COM13 reset` |
| 写固件报地址错误 | 完整镜像应烧到 0x0 | 不要用 0x1000 |

**思考题**
1. 为什么这个固件要从 0x0 而不是 0x1000 开始烧？
2. 出厂固件与 MicroPython 固件的区别是什么？

**拓展任务**：用 `python -m mpremote connect COM13 exec "print(1+1)"` 完成一条不进入交互界面的验证命令。

## 实验二：点亮板载 RGB 与串口标识

**实验目的**
1. 掌握 `machine.Pin` 与 `neopixel.NeoPixel` 的基本用法（板载 RGB 在 **GPIO48**）。
2. 编写并部署第一个 `main.py`（绿色 500ms 闪烁 + 串口同步标识）。
3. 体验"改代码 → 部署 → 复位 → 观察"的完整循环。

**知识准备**：RGB 三个通道各 0–255；本课程练习亮度建议 ≤100，避免刺眼。

**任务与步骤**

1. 在电脑上新建 `student_blink.py`：
   ```python
   from machine import Pin
   from neopixel import NeoPixel
   import time

   np = NeoPixel(Pin(48, Pin.OUT), 1)      # 板载 WS2812 接 GPIO48

   while True:
       np[0] = (0, 100, 0)                 # 绿色（低亮度）
       np.write()
       print("[GREEN ON]")
       time.sleep_ms(500)

       np[0] = (0, 0, 0)                   # 熄灭
       np.write()
       print("[GREEN OFF]")
       time.sleep_ms(500)
   ```
2. 上传为设备端 `main.py` 并复位（**分两次连接**执行）：
   ```powershell
   python -m mpremote connect COM13 cp student_blink.py :main.py
   python -m mpremote connect COM13 reset
   ```
3. 观察灯是否按 500ms 闪烁，串口是否输出 `[GREEN ON]` / `[GREEN OFF]`。
4. 把颜色分别改为红色 `(100, 0, 0)`、蓝色 `(0, 0, 100)`、黄色 `(100, 100, 0)`，每次重新上传并观察。
5. 在串口标识中加入 ANSI 颜色（选做）：
   ```python
   print("\x1b[1;32m[GREEN ON]\x1b[0m")
   ```

**验收标准**
- [ ] 板载 RGB 以自选颜色和 500ms 周期闪烁。
- [ ] 串口同步显示开/关标识，并解释 `(0,0,0)` 为什么等于熄灭。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| 灯不亮 | 引脚写错 | 确认是 GPIO48，不是 GPIO2 |
| 上传后无变化 | 上传的不是 `:main.py` | 设备端入口必须叫 `main.py` |
| 灯颜色发白刺眼 | 三通道都很大 | 练习时把值压到 ≤100 |
| 程序没启动 | 上传后停在 REPL | 单独执行一次 `reset` |

**思考题**
1. 若想让灯"一闪一灭各 100ms"，修改哪一行？实际观感与 500ms 有何不同？
2. 三个通道相等时为什么显示为白光（或灰光）？

## 实验三：MicroPython 编程与自定义闪烁

**实验目的**
1. 用变量、`while`、函数组织程序，理解"参数化"的好处。
2. 实现一个可复用的闪烁函数，并按顺序播放多种颜色。

**任务与步骤**

1. 把实验二的代码改写为函数形式：
   ```python
   from machine import Pin
   from neopixel import NeoPixel
   import time

   np = NeoPixel(Pin(48, Pin.OUT), 1)

   def flash(rgb, period_ms, times):
       """rgb 闪烁 times 次，每次亮/灭各 half 个周期。"""
       half = period_ms // 2
       for _ in range(times):
           np[0] = rgb
           np.write()
           time.sleep_ms(half)
           np[0] = (0, 0, 0)
           np.write()
           time.sleep_ms(half)

   while True:
       flash((0, 100, 0), 500, 2)    # 绿 2 次
       flash((100, 100, 0), 250, 4)  # 黄 4 次（快闪）
       flash((100, 0, 0), 1000, 1)   # 红 1 次（慢闪）
   ```
2. 上传、复位、观察顺序是否正确。
3. 增加一个函数 `solid(rgb, seconds)` 实现常亮一段时间，并把"绿闪烁→黄快闪→红慢闪→蓝常亮"编成一段小灯效。
4. 故意制造一个错误（如把 `range(times)` 写成 `range(tims)`），观察板子的报错信息，再修正。

**验收标准**
- [ ] 三种以上颜色的灯效按顺序正确播放。
- [ ] 能说出函数参数 `rgb / period_ms / times` 各自控制什么。
- [ ] 记录一次报错与修复过程。

**思考题**
1. `time.sleep_ms(500)` 与 `time.sleep(0.5)` 有什么区别？
2. 如果 `times=0` 会发生什么？为什么？

## 实验五：串口心跳与协议初识

**实验目的**
1. 会用脚本读取并给串口数据加时间戳。
2. 观察心跳 `DATA <NAME> <seq>`（每 4 秒）和闪烁标识。
3. 理解行协议：一行一条消息、以换行结束、字段以空格分隔。

**前提**：实验一~五请保持板子上没有 `wifi_config.py`（固件在无 WiFi 配置时才会把 `DATA` 心跳打印到串口）；该文件在第 6 周实验六创建并上传。

**任务与步骤**

1. 编写串口监视脚本 `serial_monitor.py`：
   ```python
   import sys
   import time
   import serial

   port = sys.argv[1] if len(sys.argv) > 1 else "COM13"
   ser = serial.Serial(port, 115200, timeout=1)
   t0 = time.time()
   print("listening", port)
   while True:
       line = ser.readline().decode(errors="replace").strip()
       if line:
           print("%7.2f  %s" % (time.time() - t0, line))
   ```
   （需要 `python -m pip install pyserial`。）
2. 运行并观察 10 秒：`python serial_monitor.py COM13`
   - 记录两次 `DATA GREEN <seq>` 的时间间隔与序号变化。
3. 对照代码找协议：在 `common/board_common.py` 中搜索 `DATA`、`HELLO`、`send(`，指出每条协议行的字段含义。
4. 阅读 `AGENTS.md` 的指令表，抄写你最喜欢的 3 条指令并说明用途。
5. （演示）REPL 中直接测试解析器：
   ```python
   >>> import board_common as bc
   >>> s = bc.StyleSet((0, 100, 0))
   >>> s.apply("COLOR 255 0 0")
   >>> s.rgb
   ```
   观察 `StyleSet` 如何把一行文本变成状态。

**验收标准**
- [ ] 提交带时间戳的心跳日志（至少 3 条 `DATA`）。
- [ ] 能解释 `DATA GREEN 7` 的含义；能说出协议为什么用行文本而不是二进制。

**思考题**

## 实验六：WiFi 联网与 TCP 通信

**实验目的**
1. 配齐 `common/wifi_config.py`（SSID / PASSWORD / SERVER_IP / SERVER_PORT）。
2. 观察板端联网与连接过程（`link up`、失败重试）。
3. 用一个最小 TCP 服务器接收板子的 `HELLO` 与 `DATA`，并回发一条指令（观察灯变化）。

**任务与步骤**

1. **安全提醒**：`wifi_config.py` 是本地密钥文件，不提交、不截图、不投屏。教师提供本组的热点 SSID/密码与电脑 IP。
2. 编辑 `common/wifi_config.py`（示例结构，值按实际填写）：
   ```python
   SSID = "lab-2g"
   PASSWORD = "<本组热点密码>"
   SERVER_IP = "192.168.1.100"   # 教师电脑的局域网 IP
   SERVER_PORT = 6000
   ```
3. 在 Windows 上运行最小测试服务器 `mini_server.py`（教师提供/学生输入）：
   ```python
   import socket

   srv = socket.socket()
   srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
   srv.bind(("0.0.0.0", 6000))
   srv.listen(2)
   print("listening on 6000")
   while True:
       conn, addr = srv.accept()
       print("board connected from", addr)
       conn.sendall(b"COLOR 0 100 100\n")     # 让板子变成青色
       while True:
           data = conn.recv(256)
           if not data:
               break
           print(data.decode().strip())
   ```
4. 重新部署绿板（带上 WiFi 配置）并复位：
   ```powershell
   python tools\deploy.py COM13 green
   ```
5. 观察三处：
   - 板子串口：`link up 192.168.1.100:6000`；
   - 测试服务器：`board connected from ...`，随后打印 `HELLO GREEN`、`DATA GREEN 1...`；
   - 板子灯：收到 `COLOR 0 100 100` 后变成青色（串口打印 `[RX GREEN]`；若发送的是带回复的指令，服务器还能看到 `STYLE-OK ...`）。
6. 拔掉服务器（Ctrl-C）再启动，观察板子每 4 秒重试并自动重连。

**验收标准**
- [ ] 板子成功连接并发送 `HELLO`（服务器日志为证）。
- [ ] 从电脑发出的 `COLOR` 指令改变了板子颜色。
- [ ] 能演示断线后自动重连。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| `wifi connect timeout` | SSID/密码错误或 5G 频段 | 确认热点为 2.4G、密码正确 |
| `connect failed: ECONNABORTED` | 服务器不在/防火墙拦截 | 先在本机 `ping` 板子 IP，再检查服务器与防火墙 |
| 连上但没有 `link up` | SERVER_IP 写的是 WSL 的 IP | 见实验七：应写 Windows 电脑的局域网 IP |

**思考题**
1. 为什么板子要主动"连出去"（客户端），而不是电脑主动"连进来"（服务器）？（提示：板子在 NAT 后面）
2. `HELLO` 为什么必须放在第一行？

## 实验七：网络链路排障与转发器

**实验目的**
1. 理解"板子 → Windows → WSL"的完整链路，以及为什么需要转发器。
2. 掌握分层排障法并完成全栈联通：两块板注册到 ROS 2 服务器。

**背景**：实验六中板子连的是 Windows。ROS 2 运行在 WSL 中，而 WSL 镜像网络下局域网设备直接访问 WSL 的端口会被拦（Hyper-V 防火墙），因此用 Windows 转发器把 `LAN:6000` 转到 `WSL:6001`。

**任务与步骤**

1. 启动 Windows 转发器：
   ```powershell
   python tools\tcp_forwarder.py --listen 0.0.0.0:6000 --target 127.0.0.1:6001
   ```
   看到 `forwarding 0.0.0.0:6000 -> 127.0.0.1:6001`。

   > 安全提示：该转发器无鉴权且监听所有网卡，只允许在隔离的实验局域网中运行，不要接入不受信任的网络。
2. 启动 WSL 全栈：
   ```bash
   source /opt/ros/jazzy/setup.bash
   cd /mnt/c/vibecoding/esp32s3/ros2_ws
   colcon build
   source install/setup.bash
   ros2 launch board_bridge wifi.launch.py
   ```
3. 部署两块板（WiFi 配置中的 `SERVER_IP` 必须是 **Windows 的局域网 IP**）：
   ```powershell
   python tools\deploy.py COM13 green
   python tools\deploy.py COM14 blue
   ```
4. 观察 `wifi_server` 日志：应在若干秒内看到 `green registered` 与 `blue registered`；`relay` 应出现 `green -> blue: FROM GREEN ...` 与反向转发。
5. 故障演练（教师指定，不真断网也可）：故意先不启动 WSL 服务器 → 观察板子 `connect failed` → 启动服务器 → 观察自动恢复。记录时间。
6. （实验六与七的分工）验证层面：
   - 板子联网：串口 `link up`；
   - 转发器：日志 `board connection from ...`；
   - WSL：`ros2 topic list | grep board` 应出现 4 个话题 `/board/green/rx`、`/board/green/tx`、`/board/blue/rx`、`/board/blue/tx`。

**验收标准**
- [ ] `wifi_server` 日志出现两块板 `registered`，`relay` 出现双向转发。
- [ ] 提交"现象—假设—验证—结论"排障记录（不少于 4 条假设）。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| 转发器没有 `board connection` | 板子没连上或 SERVER_IP 错 | 检查板子串口日志，确认 IP 是本机 WLAN IP |
| 没看到 `registered` | WiFi/密码/防火墙 | 用实验六的 mini_server 先单独验证 WiFi 通 |
| WSL IP 变化 | WSL 重启后 IP 变了 | 与课程无关（板子连 Windows）；浏览器访问才需要 WSL IP |
| 占用 6000/6001 | 上次进程未退出 | 关闭旧窗口或换端口（同时改配置） |

**思考题**
1. 如果不使用转发器，还有什么办法让板子连到 WSL？（提示：管理员权限、桥接网络）
2. 为什么转发器只转发 TCP 连接，而不需要理解协议内容？

## 实验八：ROS 2 工作空间与话题

**实验目的**
1. 熟悉 `ros2_ws/` 目录与 `colcon build`。
2. 使用 `ros2 topic` 命令查看、发布、订阅话题消息。
3. 通过 `/board/<board>/tx` 向真实板子发送第一条 ROS 2 控制指令。

**前提**：实验七的链路已打通，两块板显示 online（后续实验十一可在页面确认）。

**任务与步骤**

1. 构建工作空间：
   ```bash
   cd /mnt/c/vibecoding/esp32s3/ros2_ws
   colcon build
   source install/setup.bash
   ```
2. 查看话题：
   ```bash
   ros2 topic list
   ros2 topic info /board/green/rx
   ros2 topic echo /board/green/rx       # 应看到心跳 DATA GREEN ...
   ```
3. 发布消息（**注意引号与消息格式**）：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'COLOR 255 0 0'}"
   ```
   观察绿板变成红色。注意：`COLOR`/`PERIOD`/`RESET` 属于快捷键，板端**不回包**（板子串口会打印 `-> style=...`）；若要在 `rx` 中看到回复，可再发一条 `STYLE LIST`，会收到 `STYLE ...`、`MIXING`、`PLAYING`、`STYLE-END` 多行。
4. 连续发布（每 1 秒一条）：
   ```bash
   ros2 topic pub -r 1 /board/green/tx std_msgs/String "{data: 'PERIOD 200'}"
   ```
   观察闪烁加快后按 `Ctrl-C` 停止。
5. 使用 `RESET` 恢复默认：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'RESET'}"
   ```

**验收标准**
- [ ] `ros2 topic echo` 截图中能看到自己板子的心跳 `DATA GREEN <seq>`，以及 `STYLE LIST` 的多行回复。
- [ ] 成功用命令行改变板子颜色和周期，并成功 `RESET`。
- [ ] 能解释为什么发到 `tx`、回报在 `rx`。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| `ros2: command not found` | 没 source 系统或工作空间 | 先 `source /opt/ros/jazzy/setup.bash`，再 source 本工作空间 |
| 发了消息但板子没反应 | 板子离线 | `wifi_server` 日志会提示 `offline, dropping` |
| 话题不存在 | `wifi.launch.py` 没启动 | 先启动 launch |

**思考题**
1. `ros2 topic pub --once` 与 `-r 1` 有什么区别？
2. 如果两个终端同时向同一个 `tx` 发消息，板子会怎样？（结合行协议思考）

## 实验九：桥接节点解析与 LED 控制

**实验目的**
1. 读懂 `wifi_server.py`：TCP 行如何变成 ROS 2 消息，`tx` 又怎样写回板子。
2. 理解 `relay` 节点的板间转发（`FROM <NAME> <seq>`）。
3. 给板端增加一条自定义指令并完成端到端联调。

**任务与步骤**

1. 代码走读（对照源码填表）：

   | 代码位置 | 作用 |
   |---|---|
   | `accept_loop` / `handle_client` | 接受连接、处理注册与逐行解析 |
   | `HELLO` 分支 | 把连接登记为 green/blue |
   | `publish(String(...))` | 把一行数据发布到 `/board/<board>/rx` |
   | `make_tx_callback` | 订阅 `/board/<board>/tx` 后 `sendall` 到板子 |
   | `relay.py` | 监听 rx，改写为 `FROM ...` 发给对板 |

2. 修改板端代码，增加一条指令（示例：在 `StyleSet.apply()` 的分支中加）：
   ```python
   elif cmd == "PING":
       return ["PONG"]
   ```
3. 重新部署到绿板。先开一个终端持续订阅回传（能看到后 Ctrl-C 退出）：
   ```bash
   ros2 topic echo /board/green/rx
   ```
   再开另一个终端发送指令，观察回传中出现 `PONG`：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'PING'}"
   ```
4. 观察板间转发：绿板的心跳 `DATA GREEN <seq>` 会以 `FROM GREEN <seq>` 出现在蓝板串口日志（`[RX BLUE] FROM GREEN ...`），反之亦然。
5. （可选）故意发送一条不存在的样式指令：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'STYLE USE nope'}"
   ```
   观察 `STYLE-ERR no-such-style`，理解错误回复的价值。

**验收标准**
- [ ] 填完代码走读表并能口头解释 `rx`/`tx` 两个方向。
- [ ] 自定义指令（如 `PING`→`PONG`）联调成功，截图包含发送与回复。
- [ ] 能指出板间 `FROM` 消息出现的位置。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| 发送后无回复 | 板子离线或指令拼写错误 | 先看 `wifi_server` 日志；确认指令全大写 |
| `PONG` 没出现 | 别忘了重新部署并复位板子 | `python tools\deploy.py COM13 green` |
| relay 没转发 | 只有另一个板在线时才会转发 | 确认两块板都 registered |

**思考题**
1. 如果要在板子离线时给用户提示，应该在哪一层做？（结合 `wifi_server` 的 `offline, dropping` 日志）
2. `relay` 为什么不直接让两块板互连，而是经过 ROS 2 中转？

## 实验十：样式管理、轮播与并行混合

**实验目的**
1. 掌握 `STYLE SET/DEL/USE/LIST` 与 `default` 保护。
2. 理解"保存与应用分离"的设计。
3. 用 `PLAY` 轮播、`MIX` 并行混合体验"时间合成"，并与理论计算对照。

**任务与步骤**

1. 先在终端 B 持续订阅回传：
   ```bash
   ros2 topic echo /board/green/rx
   ```
   在终端 A 发送查询：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'STYLE LIST'}"
   ```
   在 B 中找到 `STYLE default 0 100 0 500 blink 1`、`MIXING -`、`PLAYING -`、`STYLE-END n`
   （心跳 `DATA` 行会穿插出现，属于正常现象）。
2. 保存三条样式（**保存不会改变当前闪烁**）：
   ```bash
   # 红，快闪
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'STYLE SET red 255 0 0 120 blink'}"
   # 蓝，常亮
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'STYLE SET blue 0 0 255 500 solid'}"
   # 黄，慢闪
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'STYLE SET yellow 255 150 0 800 blink'}"
   ```
   确认灯仍保持原来的绿色闪烁（保存不切换）。
3. 应用与恢复：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'STYLE USE red'}"
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'RESET'}"
   ```
   确认 `RESET` 后回到绿闪，且 `red/blue/yellow` 都还在。
4. 保护验证：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'STYLE DEL default'}"
   ```
   应收到 `STYLE-ERR protected`。
5. 轮播与混合：
   ```bash
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'PLAY red yellow blue'}"
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'PLAY STOP'}"
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'MIX red blue'}"
   ros2 topic pub --once /board/green/tx std_msgs/String "{data: 'MIX STOP'}"
   ```
   观察：轮播是"依次切换"，混合是"实时合成"（红灭蓝亮时显蓝、红蓝重叠时显紫）。
6. 记录 10 秒观感，与课后计算结果对照。

**验收标准**
- [ ] `STYLE LIST` 中三条自定义样式 + `default` 共存，`default` 不可删除。
- [ ] 演示轮播与混合各一次，并解释两者差别。
- [ ] 口述 `MIX` 的合成规则（亮灭 OR、颜色相加截断）与最小采样间隔（20ms）。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| 保存后灯就变了 | 误用了会切换的旧界面/指令 | 用 `STYLE SET` 只保存；切换必须 `STYLE USE` |
| `STYLE-ERR bad-name` | 名称含非法字符/超 16 字符 | 只用字母、数字、`_`、`-` |
| 混合颜色偏白 | 相加截断饱和 | 降低各样式亮度或用 `MIX` 两条对比色 |

**思考题**
1. 红(100ms) + 蓝(300ms) 混合时，写出 0–600ms 每个时段的合成颜色。
2. 为什么要把混合的采样间隔限制在 20ms，而不是 1ms？

## 实验十一：Web 控制台与人机交互

**实验目的**
1. 启动 `led_ui` 并完成样式管理、轮播、混合、恢复默认的完整操作。
2. 理解浏览器 → HTTP API → ROS 2 话题 → 板子的数据流。
3. 了解安全与体验设计：本机绑定、禁用缓存、在线状态。

**任务与步骤**

1. 启动全栈（若已启动可跳过）：
   ```bash
   UI_HOST=0.0.0.0 ros2 launch board_bridge wifi.launch.py
   ```
   在 Windows 浏览器打开 `http://<WSL的IP>:8080`（WSL 中运行 `hostname -I` 获取 IP；本机直连调试可用默认 `127.0.0.1:8080`）。

   > 安全提示：`UI_HOST=0.0.0.0` 会把**无鉴权**的控制页面暴露给整个局域网，仅限隔离的实验局域网、经教师确认后使用；平时保持默认 `127.0.0.1`（见教师手册 §九）。
2. 页面操作清单（全部完成后截图）：
   - [ ] 观察两块板的在线状态徽标；
   - [ ] 新建样式（如 `show 255 100 0 300 blink`）→ 点 `保存样式` → 确认当前闪烁未被改变；
   - [ ] 点该样式的 `应用` → 灯切换；
   - [ ] 勾选 2–3 条样式 → `轮播所选` → `停止轮播`；
   - [ ] 勾选 2 条 → `混合所选` → `停止混合`；
   - [ ] 点 `恢复默认` → 回到原始绿/蓝闪烁。
3. 在线状态实验：把一块板断电（拔 USB 或断电重启），等待 10 秒以上，观察页面徽标变为"离线"；恢复供电后等待重新上线。
4. 安全/体验观察：打开浏览器开发者工具 Network 面板，查看页面响应头中的 `Cache-Control: no-store`；讨论：如果去掉它会有什么问题？
5. （选做）界面改进：例如在卡片上显示最近一次 `DATA` 的时间，或增加常用颜色快捷按钮。改动 `led_ui.py` 后重新 `colcon build` 并刷新页面（记得先 `Ctrl-F5`）。

**验收标准**
- [ ] 用页面完成上述 6 项操作并演示给教师。
- [ ] 能画出并讲解浏览器到板子的完整数据流。
- [ ] 能说明"离线"判定的依据（心跳超时）与"保存不覆盖"的意义。

**常见问题**

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面打不开 | WSL 镜像网络下 localhost 不通 | 用 WSL 的 IP 访问；或确认 `UI_HOST=0.0.0.0` |
| 改了页面还是旧的 | 浏览器缓存 | `Ctrl-F5` 强刷（服务端已加 no-store） |
| 刷新后样式变多 | 旧版页面的解析 Bug | 强刷加载新页面；服务端已按名字去重 |
| 页面按"保存"后灯变了 | 点成了"应用/保存并应用" | 只点 `保存样式`；切换用列表中的 `应用` |

**思考题**
1. 如果想让手机也能控制，需要改什么？有什么安全风险？
2. 页面应该如何提示"指令已发出但板子离线"？
